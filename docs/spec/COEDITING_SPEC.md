# 同時編集（Google ドキュメント式）の設計 v1.1

> **状態**: PR0・PR1 は実装済み（PR2・PR3 は未着手）
> **最終更新**: 2026-09-16
> **対象**: 議事録（`meetings.minutes_md`）→ Wiki（`wiki_pages.body`）

## 0. この文書の位置づけと、着手の条件

2026-09-13 に「同時に書いても黙って消えない」ための歯止めを本番へ入れた（[3 章](#3-いまの床2026-09-13-に本番へ入れた歯止め)）。そのうえでユーザーから「**不具合が出そうなので、Google ドキュメント式の設計を先に考えておきたい**」という指示が出たため、この文書を書いた。

**着手の条件（ここが決まらないと作らない）**

> **「会議中に、2人以上が同じ議事録を同時に打つ」場面を製品として狙うのか。**

- **狙うなら作る価値がある。** いまの床では、2人が同時に打つと1〜2秒ごとに競合の帯が出て実用にならない。
- **狙わない（1人が書いて、AI秘書が末尾に足すだけ）なら作らない。** その形はいまの床で足りている。

**2026-09-16 に「狙う」と決まった**（ユーザー指示）。PR0 は 2026-09-15 に本番へ入っており、PR1 をこの決定のあとに実装した。

## 1. 決定

**議事録から入れる。正本はいまの列（`meetings.minutes_md`）のまま変えない。Y.Doc（CRDT の器）は「編集している間だけ生きる合流の器」とし、DB には積まない。運びは Supabase Realtime の broadcast（既存の private チャネルに相乗り）。列への書き込みは参加者のうち1人（＝書記）だけが行い、外からの書き込みは書記が代表して取り込む。**

### 前回（2026-09-13）の裁定から判断を変えた理由

前回は「CRDT は入れない。書き手を1人に寄せる」だった。変わった前提は3つ。

1. **新しい依存が要らない。** `yjs@13.6.29` / `y-prosemirror` / `y-protocols` は **BlockNote 0.46.2 の依存として既に入っている**（`npm ls yjs` で1本に重複排除されていることを確認済み）。BlockNote 自身が `collaboration` オプションを持つ。
2. **「正本が二重になる」が起きない形がある。** Y.Doc を永続化しなければ、DB から見た正本は列1つのまま（案 ii）。前回の却下理由はこの案には当たらない。
3. **落ちる先の床ができた。** 楽観ロック・世代ガード・タスク化の検査が本番に入った。同時編集はその上に載せる層で、外せば床に戻る。

## 2. いまの正本と、外から本文を書く経路

| | 正本 | 形 | 機械が読む契約 |
|---|---|---|---|
| 議事録 | `meetings.minutes_md` | Markdown のテキスト1列 | **ある**（下記） |
| Wiki | `wiki_pages.body` | BlockNote のブロック JSON 文字列 | 無い |

**議事録の Markdown の契約**（壊すとタスク化が壊れる）

- `- [ ] SPEC(パス): 決めること` の行を DB 関数 `rpc_parse_meeting_minutes` が1行ずつ正規表現で読んでタスクを作る。
- 作成済みの行は**行末の `<!--task:uuid-->`** で判別する（二重作成防止）。TS の `SPEC_LINE_REGEX` / `TASK_MARKER_REGEX` と SQL のパターンが一致していることをテストで検査している。
- Markdown ⇄ ブロックの変換は自前の決定的な純関数 `src/lib/minutes/markdown.ts`。

**外から本文を書く経路（全部生きている）**

| 経路 | 書き方 | 版の確認 |
|---|---|---|
| MCP/CLI `minutes_update` / `wikiUpdate` | 全文差し替え | **任意**（2026-09-15 の PR0 で `expectedUpdatedAt` を追加。渡さなければ今までどおり無条件） |
| MCP/CLI `minutes_append` → `rpc_minutes_append` | `本文 || E'\n\n' || 追記` | 無し（追記なので衝突しない） |
| 同上・RPC が使えないときの回り道（`minutes.ts` の catch） | **読んでから全文差し替え** | 無し |
| チャット秘書（LINE/Slack） | 上の MCP を通る（議事録へ直に書く道は無い） | 同上 |
| `rpc_parse_meeting_minutes`（タスク化・画面） | 全文を書き戻す | **あり**（2026-09-13 に追加。渡された本文が DB と違えば止める） |
| `rpc_parse_meeting_minutes_as`（タスク化・CLI/秘書 `minutes_taskify`） | 同上 | 同上 |
| `rpc_set_spec_state`（Wiki） | 本文の末尾にブロックを追記 | 無し |
| 相手先ポータル | 読むだけ | — |

## 3. いまの床（2026-09-13 に本番へ入れた歯止め）

同時編集を入れても**この床は残す**。外したら床に戻るだけ、という関係にする。

- **議事録**: `updated_at` の楽観ロック（BEFORE UPDATE トリガーあり）。競合したら帯＋「書きかけをコピー」「最新を読み込む」。AI秘書の末尾追記だけは自動で取り込む（`theirs.startsWith(base + '\n\n')` のときだけ、生きているエディタの末尾へ `editor.insertBlocks` で差し込む）。タスク化の DB 関数は渡された本文が DB と違えば何も書かずに止める。
- **Wiki**: 本文保存の楽観ロック・ページの世代ガード・「開いたとき／直前の保存と同じ内容なら保存しない」比較（キー順を揃えてから）・削除されたページの判別。
- **在席表示**: private チャネル `meeting-minutes:<meetingId>`、`realtime.messages` に `extension='presence'` の select/insert ポリシー（`app_can_track_meeting_minutes(topic)` ＝ `app_can_write_space` ＋ MFA）。購読前に `supabase.realtime.setAuth(token)` へ本人の JWT を**引数で**渡す。
- 議事録・Wiki とも**編集は止めない**（知らせるだけ）。

## 4. 却下した案

| 案 | 却下の理由 |
|---|---|
| Y.Doc を正本にし、列は射影にする | DB 関数と MCP の書き込み経路をすべて Node 側に作り替えることになる。公開済みの CLI/MCP も壊れる |
| Y.Doc を永続化しつつ列にも射影を書き続ける | 正本が2つになる。外から列だけ変わったときに器を作り直す必要が残る（前回の却下理由がそのまま残る） |
| 常駐の WebSocket サーバー（Hocuspocus 等）を建てる | 権威と順序は得られるが、ホスト・監視・費用が新規に発生する。実害が未観測の段階では過大。**差し替え口だけ残す**（`CollabTransport`） |
| 参加者が各自で列に保存する | 楽観ロックで互いを弾き合う。書記1人に集約する |
| Realtime を使わず行単位の3方向マージ | 「打っている途中で相手の文字が見える」にならない。求めている形ではない |
| Wiki から先に入れる | 同時に打つ場面は会議の議事録。土台（チャネル・ポリシー・差し込み口）も議事録側に既にある |

## 5. 設計

### 5.1 データモデル（新しい表は作らない）

変えるのは3点だけで、いずれも捨てられる。

1. **`realtime.messages` のポリシーの条件を広げる**。既存2本の `extension = 'presence'` を `extension in ('presence','broadcast')` に。判定関数 `app_can_track_meeting_minutes(text)` はそのまま使い回す。Wiki は3段目で `app_can_track_wiki_page(text)`（topic `wiki-page:<uuid>`・`app_can_write_space(page.space_id, page.org_id)` ＋ `mfa_satisfied()`）を同形で足す。
2. **MCP/CLI に合言葉を足す**（PR0）。`minutes_get` が `updated_at` を返し、`minutes_update` / `wikiUpdate` が任意の `expected_updated_at` を受ける。不一致なら 409。まず任意にし、CLI の版が行き渡ってから必須へ。
3. **機能フラグ**。1段目は環境変数 `NEXT_PUBLIC_COLLAB_MINUTES_ORG_IDS`（org ID の CSV）。列は足さない。2段目で space 単位にするなら `spaces.collab_enabled boolean default false` を1列。

### 5.2 モジュール構成（`src/lib/collab/`・React 非依存）

| ファイル | 役割 |
|---|---|
| `transport.ts` | `CollabTransport`（`join` / `leave` / `send` / `on`）と Supabase 実装。チャネルは既存の `meeting-minutes:<id>`、`config: { private: true, broadcast: { self: false, ack: false } }`。購読前に `setAuth(token)`。バイト列は base64 |
| `session.ts` | Y.Doc の生涯。イベントは `y-sync1`（状態ベクトル）/ `y-sync2`（差分）/ `y-update` / `y-aware`。文字の更新は 300ms でまとめて送る（`Y.mergeUpdates`）。カーソル（`y-aware`）は動いたときだけ、1秒に1回まで送る（数の根拠は 5.9）。受信の `Y.applyUpdate` は try/catch で包み、壊れた更新は捨てる |
| `seed.ts` | 列から Y.Doc への**決定的な**種まき（5.3） |
| `scribe.ts` | 書記の選出と保存（5.4） |
| — | `meta`（Y.Map）に `seedHash` / `savedAt`（列の updated_at）/ `savedHash` / `freeze` を持ち、全員に伝える |

**遅れて参加した人**: `y-sync1` を送り、**書記だけ**が `y-sync2` で返す（全員が返すと人数倍になる）。2秒で返事が無ければ1回だけ再送、それでも無ければ列から種をまく。返す `y-sync2` は1万3千字の議事録で約155KB、10万字で約1.3MB（実測・5.9）。Pro の1回の上限 3,000KB に収まるので分割しない。

### 5.3 種まきの決定性（ここが Yjs でいちばん踏みやすい穴）

2人が同時に列から別々に Y.Doc を作って合流すると、**本文が二重になる**。

**対策**: 同じ本文からは byte 単位で同じ更新を作る。専用の `seedDoc` を作り、`seedDoc.clientID = fnv32(sha256(本文))` に固定してから種をまく。Yjs は `(clientID, clock)` が同じ構造体を重複として捨てるので、同じ本文から作られた2つの種は合流しても1つになる。

**変換の経路は実物で確認済み**（2026-09-14）:

```
minutes_md
  → parseMinutesMarkdown()            // src/lib/minutes/markdown.ts（自前・決定的）
  → BlockNote のブロック
  → blockToNode()                     // @blocknote/core が export している
  → ProseMirror のノード
  → prosemirrorToYXmlFragment()       // y-prosemirror が export している
  → Y.XmlFragment
```

`meta.seedHash` に本文のハッシュを書き、**合流後に異なる `seedHash` が2つ見えたら「種が2つある」と検知**して、書記が列から作り直す（帯を出す）。

### 5.4 書記（列に保存する1人）

- **選び方**: presence の参加順がいちばん古い人。全員が同じ presence 状態から同じ答えを出すので、投票も合意形成も要らない。
- **保存**: Y.Doc の変更から 1.5 秒静止で `serializeMinutesBlocks(editor.document)` → 既存の保存経路（`.eq('updated_at', meta.savedAt)`）。成功したら `meta.savedAt` / `meta.savedHash` を更新する。
- 書記以外は保存しない。ただし `pagehide` のとき、自分の内容が `savedHash` と違えば保存を試みる。
- 競合しても、DB の本文が自分の内容と**等しければ競合扱いしない**。
- 書記が消えたら、presence の離脱で次の人が引き継ぎ、**即時に1回保存する**。

### 5.5 外からの書き込みがセッション中に来たとき（この設計の核心）

**検知**: (a) 書記の保存が0行（競合）、または (b) 書記が10秒ごとに `updated_at` だけを読む軽い問い合わせ。2段目では `realtime.send`（**本番の DB に存在することを確認済み**）を `meetings` の after update トリガーから呼び、ポーリングをやめる。

検知したら、**書記が代表して**次の順で処理する。

| 相手 | DB の本文の形 | 書記の処理 | 失われるもの |
|---|---|---|---|
| `rpc_minutes_append`（秘書・MCP の追記） | `base + '\n\n' + 追記` | 既存の `appendMarkdown` を**書記だけ**が呼んで Y.Doc に差し込む（全員に伝わる） | なし |
| タスク化の書き戻し | base と**行末の目印だけ**が違う | `diffTaskMarkers(base, theirs)` で `[{行の本文, taskId}]` を取り出し、同じ本文で目印の無い最初のブロックに差す。1つでも差せなければ下の全文差し替えへ落とす | なし |
| `rpc_set_spec_state`（Wiki・3段目） | `base のブロック列 + 末尾ブロック` | 末尾のブロックを書記が `insertBlocks` | なし |
| MCP の全文差し替え | 上のどれでもない | Y.Doc の内容が `savedHash` と同じなら黙って置き換える。違えば置き換えたうえで**いまの帯**（「書きかけをコピー」）を全員に出す | 最後の保存からの1.5秒以内の分。帯とコピーがあるので黙っては消えない |

### 5.6 権限の境界

- 送受信できるのは `app_can_track_meeting_minutes` が true の人だけ（社内の admin/editor ＋ MFA 済み）。**相手先（client）・閲覧者（viewer）・他組織・未ログインは当てはまるポリシーが無いので参加できない**（いまの在席表示と同じ仕組み）。
- Supabase は private チャネルの判定を**参加時**に行い、トークンの更新まで持ち越す。**役割を落とされた人が最長1時間、更新を受け取り続ける**。ただし列への保存は表の RLS で止まるので正本は守られる。**この残りは受け入れる**（仕様として明記する）。
- サーバー側の権威は無い（壊れた更新を送られても防げない）。ただし**同じ組織の editor はいまでも本文を丸ごと上書きできる**ので、権限の拡大にはならない。壊れた更新は `applyUpdate` の例外で捨て、直列化に失敗したら縮退する。

### 5.7 Markdown の契約を壊さない保証

Y.Doc が扱うのは BlockNote のブロック木で、`- [ ] SPEC(...)` はチェックリストのブロック、`<!--task:uuid-->` は**それ以上分割されない inline ノード**（`taskMarker`）。同時に打っても、目印が分裂したり中身が変わることはない。

不変条件は **Y.Doc から列への唯一の出口＝書記の保存**に集める。保存の直前に `assertMinutesInvariants(md)` を通す。

1. 同じ `task:uuid` が2回出ない
2. 目印は行末にしかない
3. `serializeMinutesBlocks(parseMinutesMarkdown(md)) === md`（往復で変わらない）

1つでも破れたら**保存せず帯を出して縮退する**。

**タスク化の最中だけ順序を固定する**: 書記が `meta.freeze = 'parsing'` を立てて全員のエディタを一時的に読み取り専用（2秒以内）→ 保存を流し切る → RPC → 目印を差す → `freeze` を下ろす。この間に誰かが行を編集して目印が迷子になる窓を消す。MCP/CLI からタスク化を呼ばれた場合は `freeze` が効かない（その場合は 5.5 の2行目の取り込みに落ちる）。

### 5.8 縮退（いまの床へ落ちる道）

次のどれかで「1人で書くいまの形」へ落とし、帯で知らせる。

- Realtime に5秒以内に繋がらない／`CHANNEL_ERROR`／切断が30秒続く → 自分の Y.Doc の内容を持ったまま、いまの保存経路（楽観ロック）に切り替える。再接続できたら `y-sync1` から合流し直す
- サーバーから `Too many messages per second` で切られた → プロジェクト全体が上限を超えている。全員がすぐ入り直すとまた超えるので、30〜60秒のばらつきを付けて待ってから入り直す（5.9）
- 開いている画面が6つを超えたら、7つ目以降はいまの形（読めるが輪に入らない）。数えるのは人ではなくタブ
- 直列化・不変条件の検査に失敗 → その端末だけ縮退。書記なら次の人へ譲る
- 本文が10万字を超える議事録は最初から同時編集を切る

### 5.9 通信量の見積もり（2026-09-15 に実測）

Supabase Realtime の上限は、プロジェクト全体（全顧客の合計）にかかる。1通の数え方は「送った1通＋受け取った人数分」なので、n 人の部屋で1回送ると n 通になる。

#### 1回に送る大きさ

見本 `src/__tests__/lib/minutes/fixtures/real-minutes-shape.md` を Y.Doc にして測った。大きさは base64 と Supabase の送信の枠を含む。

| 送るもの | 大きさ |
|---|---|
| 打った文字（300ms ぶんのまとめ） | 約0.2〜0.3KB |
| カーソルの位置 | 約0.5KB |
| 遅れて参加した人への全文（1万3千字） | 約155KB |
| 同（10万字） | 約1.3MB |

#### 1秒あたりの通数と、決めた上限

打っている1人につき「(文字 3.3回 ＋ カーソル 1回) × 部屋の人数」、つまり約 4.3 × n 通/秒になる。

| 部屋 | 通数/秒 |
|---|---|
| 3人のうち2人が打つ（ふつうの会議） | 約26 |
| 6人全員が打つ（人数の上限） | 約155 |
| 参考：前の案（150ms・カーソルも同じ頻度）で3人全員 | 約120 |
| 参考：前の案で8人全員 | 約850 |

**上限は500通/秒で見積もり、その半分の250通/秒に収める。** 本番は Pro・使いすぎ防止（spend cap）オンで、プロジェクトの設定値は2,500通/秒になっている。ただし公式資料の Pro は500通/秒なので、Supabase 側で下げられても困らない数で決めた。250通/秒なら、ふつうの会議が同時に9つ進んでも収まる。

#### 上限を超えたとき

判定は約1分間の平均（5秒×12区間）で、瞬間的な山はならされる。超えるとサーバーがプロジェクト内のチャネルを `Too many messages per second` で切り、いまの「書いています」表示も一緒に切れる。1秒あたりのバイト数の上限（既定100KB/秒）は、2026-09 時点の `supabase/realtime` のソースでは制限に使われていない。

#### 月の通数

3人の会議で1人が半分の時間打つと、1時間に約2.3万通になる。Pro の月500万通で約200会議時間ぶんだ。**使いすぎ防止がオンのままだと、超えた時点から次の請求期間まで Realtime が使えなくなる**（同時編集は床に落ちるが、在席表示も止まる）。利用が増えてきたら Usage 画面の Realtime Messages を見て、使いすぎ防止を外すか判断する。

## 6. 段階

| 段 | 中身 | できるようになること |
|---|---|---|
| **PR0**（済・2026-09-15） | MCP の `updated_at` 返却＋`expected_updated_at`（任意） | 同時編集が無くても、**外からの全文差し替えが黙って上書きしなくなる** |

## 7. やらないこと（期待させない範囲）

## 8. 本番で確かめること

1. 社内の editor 2人が同じ段落を60秒打ち続けて、両方の画面が一致し、3秒後の `minutes_md` が両画面と一致し、競合の帯が出ない

3. セッション中に MCP の全文差し替え → 帯が1回出て、「書きかけをコピー」で取れる
4. セッション中にタスク化 → 両方の画面に目印が出て、もう一度押しても重複したタスクが作られない
5. viewer と client のアカウントで購読が `CHANNEL_ERROR` になり、更新が届かない。MFA 未入力（aal1）も同じ
6. 2つのタブを同時に開いて（回線を遅くして）本文が二重にならない
7. 書記のタブを閉じて30秒以内に、残った人が保存する
8. wss を遮断すると帯が出て、1人用の保存（楽観ロック）が動く。再接続で合流する
9. 6人全員が打っている部屋で、Realtime の通数が250通/秒以下（5.9）。3人の会議1時間の通数が約2.3万通から大きく外れない

**前提（ここを取り違えると壊れる。2026-09-16 の裁定）**

1. **書記＝いま部屋に居る、輪に入っている人のうちいちばん古い人。据え置きはしない。**
   「いまの書記は替えない」は各自がローカルに覚えている値なので、見え方がずれると2人が
   同時に自分を書記だと思い込む。在席の一覧だけから決まる純粋な計算にする。
2. **座席＝チャネルに入る1回。** `joinedAt` は `SUBSCRIBED` のたびに取り直す。切れて
   入り直した人はいちばん新しい人になり、書記の座は残っていた人に渡る。
3. **目録（`y-sync1`）に返事をするのは、尋ねた人を除いたいちばん古い人1人。**
   全員が返すと同じ全文が人数ぶん流れ、書記だけにすると書記自身が尋ねる側のときに誰も返せない。
4. **部屋の中の人が保存した競合は、競合ではない。** 内容は器で既に合流しているので、
   基準（`updated_at`）を差し替えて書き直す。判定は `meta.savedAt` と突き合わせる。
5. **本文を作る人は選ぶ。それでも二重になったら、新しいほうに揃えて1つに戻す**
   （2026-09-17 の裁定。この取り決めを猶予時間で押さえるのは3度目の失敗だった）。

   在席には2つの印を載せる — `present`（いま開いていて加わるつもり。器の用意より
   **先に**立つ）と `collab`（本文の入った器を持っている）。規則は一文で:
   **「本文を持つ人が居ればその人に聞く。誰も持っていなければ、`collab || present` の
   うち `joinedAt → id` で先頭の1人が待たずに作る。それでも種が2つ入ったら、列の
   更新時刻が新しいほうを残して、負けたかたまりを全員が消す」**（`electSeeder` +
   `repairSeeds`）。

   **選出だけでは足りない理由**: 在席が行き渡るのに数百ミリ秒かかるので、それより
   短い間に2人が開くと、どちらの視界にも相手が居ない。選び方をどう変えても衝突は
   残るし、猶予時間を延ばしても窓がずれるだけだった。だから「起きないようにする」のを
   やめ、「起きても全員が同じ規則で1つに戻す」層を足した。

   **消す前に、残すほうを自分が持っているか確かめる。** 通は1通ずつ配られるので、
   「消す判断のもとになった印」だけ先に届いて本文がまだ来ていないことがある。そこで
   消すと**手元の本文がゼロになる**。議事録には版の控えが無いので戻せず、白紙のまま
   1行打つとその1行で列を上書きしてしまう。持っていなければ**1つも消さず**、
   列から読み直す形へ落とす。直したあとは「ちょうど1つ」を確かめる（0 も 2 も縮退）。
   どちらが新しいか分からない（基準が両方とも読めない）ときも、勝手に選ばない。

   **消せる理由**: 二重は「器の直下に本文のかたまりが2つ並んだ状態」で、各かたまりの
   持ち主は種の合言葉から決まる番号（`seedClientId`）で分かる。負けたほうを消すのは
   ただの削除なので、全員が同じ規則で消せば同じ形に落ち着き、同じものを2回消しても
   壊れない。**保存の基準（`meta.savedAt`）も残したほうに合わせる** — 合わせないと、
   消えた本文を読んでいた書記が古い基準で保存に行き、競合の帯が出続ける。
   1つ前の版が入れた印（基準を持たない数値）は、いちばん古い扱いにする。

   放っておくと何が起きるか: 「片方を消してももう片方が残る」「相手の編集が下側の複製に
   入って見えない」「気づいた側が画面を読み直す」が同時に起きる。実際にユーザーから
   3つとも報告された（2026-09-17）。

   **名乗るのは加われる画面だけ。** スマホ・器の読み込みに失敗した画面は `present` を
   名乗らない（名乗ると、加わらないのに相手を猶予切れまで待たせる）。

   **顔ぶれは覚えておいて渡し直す。** 器は使うときだけ読み込むので、できる前に在席が
   届くことがある。それは「2人がほぼ同時に開いた」場面そのもので、取りこぼすと
   「自分ひとりだ」と見えて作ってしまう。同じ理由で、返事役を決めるときは在席の一覧に
   **自分のいまの状態を重ねる**（一覧の上では本文を持った直後でも「持っていない」ままで、
   そのまま信じると持っているのに返事役から外れる）。

   読み直し（`duplicate-seed`）は**直しきれなかったときの保険**として残す。
6. **数えるのは人ではなくタブ**（2026-09-17 に変更）。同じ人がタブを2つ並べて開くのは
   普通の使い方で、人ごとに見分けると自分の2つのタブが互いを相手と見なさず、どちらも
   保存しに行って弾き合う（＝競合の帯が出続ける）。在席の鍵・書記・返事役・人数の上限は
   すべてタブごとの見分け札（`CollabPeer.id`）で決める。
   **ただし「〇〇さんが書いています」の帯は人ごとにまとめる**（自分の別タブは出さない。
   同じ人の複数タブは1人として、どれかが書いていれば「書いています」にする）。
   書記は**手前に出ているタブを先に選ぶ**。ブラウザは裏に回ったタブの時間の進みを
   間引き、数分で止めるので、裏のタブが書記だと手前で打っているのに保存だけが遅れる。
   1つ前の版の画面（見分け札を持たない相手）が部屋に居る間は、**新しい版のほうが
   輪から降りる**（`peer-outdated`）。相手を輪から外すのは誤り — 外すと「自分ひとりだ」と
   見えて目録合わせをせずに種をまき、相手の器と食い違って本文が二重になる。
   降りたら**その画面を開き直すまで戻らない**（縮退は一方通行）。古い画面が去ったあとは
   居合わせた全員が自分で保存するので、競合の帯が戻る。帯の文面で開き直しを促している。
   受け入れている見え方: 自分のもう1つのタブのカーソルが、自分の名前と色で本文に出る。
7. **カーソルの色は「空いている番号のうちいちばん小さいもの」を取り、一度決めたら
   会期中は変えない**（`colorIndexOf`）。取った番号は在席に載せて配る。
   単純に入った順で数えると、誰かが抜けたあとに入った人が残っている人とぶつかる
   （2人の部屋で先に居たほうが抜けると、次に入った人は必ず同じ番号になる）。
   並べ方は**入った順 → 名札順**だけで決める（書記の決め方とは分ける。あちらは
   「手前に出ているか」で先頭が入れ替わるので、誰かがタブを切り替えるたびに色がずれる）。
   **途中で変えられない理由**: カーソルを描く部品は相手ごとに札を1回だけ作って使い回すので、
   あとから色を変えても相手の画面には届かない（帯だけ新しい色になり、カーソルは古い色のまま）。
   受け入れている残り: 互いの在席が届く前に2人が同時に入ると重なることがある。
   そのときは**あとから入ったほうが開き直す**と空きを取り直す。
   **値は `#RRGGBB` で渡す** — 部品はこの形しか読めず、`var(--color-…)` のままだと名前の
   文字色の判定と選択範囲の色づけが壊れる。トークン（`--color-cursor-1〜6`）を正本にして、
   使うときに実際の値へ読み替える。

**設計から変えた点（実装で分かったこと）**

- 種の合言葉（`seedHash`）は sha256 ではなく **FNV-1a を2本つないだ64ビット**にした。ブラウザで同期的に計算できる必要があり、求めているのは「同じ本文か違う本文か」の判別だけのため。
- **ブロックの id も本文から決める**必要があった。BlockNote は id の無いブロックに毎回ランダムな UUID を振るので、器の clientID だけ固定しても種が別物になり二重になる。
- 5.5 の「外からの書き込みの取り込み」は**専用の処理を作らず、いまの床（`tryRebaseFromServer` → `appendMarkdown` → 競合の帯）をそのまま使う**。書記の保存が既存の保存経路を通るので、末尾追記の自動合流も競合の帯もそのまま効く。
- 種が2つ入ったときは、**新しいほうに揃えて1つに戻す**（`repairSeeds`）。列から読み直すのは、消しきれなかったときの保険に下げた。帯は出さない。
- **本文が器に届くまでエディタは書けない**（`synced`）。届く前は器が空なので、そこへ打つと、あとから届いた本文と混ざる。ふつうは1秒かからない。
- **人数の上限は、超えた側だけが輪を抜ける**（`rankOf`）。全員で落とすと、先に書いていた人まで巻き込む。
- つながった知らせは運び役が覚えておき、合流が始まった時点で渡し直す。エディタは遅延読み込みなので、**つながる方が先になる**ことがある。

- **合流は行き帰りの両方**。返す人は足りない分（`y-sync2`）と一緒に自分の目録も送り、尋ねた人は自分だけが持っている分を返す。片道だと、切れている間に入り直した本人が打った分が部屋に届かず、誰にも知らせず消える。
- **本文が器に入るまで書記として振る舞わない**（`synced`）。空の器の中身で議事録を上書きしないため。
- **タスク化のあとは部屋のみんなに読み直してもらう**（`y-reload`）。タスク化は DB 側で行末に目印を足すので、伝えないと相手の器と列がずれたままになり、それ以降その人の書いた内容がいっさい保存されない。
- **1通が大きすぎるときは、行き先で分ける**（上限 150万字・base64 換算）。`y-sync2` は空で返して「送れない」と伝え、受け手は輪に入らず1人用へ。`y-update` は打った本人が輪を抜けて自分で保存する側に回る。黙って落とすと内容が静かに消える。
- **落ちたことは在席で伝える**（`collab: false`）。伝えないと、落ちた人が書記に選ばれ続け、誰の書いた内容も列に残らない。

**残していること（PR2 以降）**

- 上限超過で切られたときの「30〜60秒のばらつきを付けて入り直す」（5.8）は入れていない。いまは2回やり直して諦め、1人で書く形へ落とす。
- 外からの書き込みを知るための10秒ごとの問い合わせ（5.5 の b）は入れていない。書記の保存が競合したときに気づく形だけ。
- **`y-reload` と種の重複で列から読み直すとき、書きかけを黙って捨てている。** 対象はタスク化した人の保存から読み直しまでの1〜2秒に他の人が打った分。既存の競合の帯と同じく「書きかけをコピー」を挟むのが筋。
- **配達に失敗した1通を取り戻す道が、入り直す以外に無い。** 握手は参加のときだけなので、落ちた1通ぶん器がずれたまま書記が保存し続けると、その段落は静かに消える。対象が2組織のうちは様子を見る。
- 在席の記録だけ残った幽霊が居ると、新しく入った人が4秒読み取り専用で待つ（返事が来ないため）。閉じたタブの在席が消えるまでの約30秒がこれに当たる。
- **二重を直すとき、負けたほうの本文は消える。** 2人が同時に開いたときは0.3〜1秒ぶんだが、
  幽霊在席で4秒待ってからまいた場合は、**その回に書いてきた本文がまるごと**負ける
  ことがある。読み直しで直していたときも同じ分を捨てていたので悪化ではないが、
  「わずかな取りこぼし」ではない。
- **直した瞬間にカーソルが飛ぶ**（本文のかたまりが1つ消えるため）。
- **猶予切れの種まきは、いまも全員が横並びで行う。** 係が2秒以内にまかなかったら
  「次の順番の1人だけ」が引き継ぐ形にすれば、最後まで「まくのは1人」を保てる。
  いまは `repairSeeds` に収束を任せている（Fable の裁定どおり）。
- **係のエディタの読み込みが遅いと、ほかの人が最大4秒読み取り専用で待つ。**
  `present` は画面が載った時点で立つが、実際にまけるのはエディタが載ってから。
  `repairSeeds` が入って「絶対に二重にしない」必要は薄れたので、待ちを縮められるかは
  実測で決める（縮めたときに `repairSeeds` が何回走るかを数える）。
