# 投票ブロック（Wiki・議事録）仕様 v1.0

2026-09-26 に要件が決まり、同日に Fable が権限の範囲・データの置き場所・同時編集との整合を裁定した。
この文書が正本。実装は §7 の順に1本ずつ PR にする。

## 1. 何ができるようになるか

Wiki と議事録の「/」メニューから投票を置ける。議題を書いておくと、読んだ人が OK・NG・保留を押し、誰が何を押したかを本文の中で見られる。

| 打つ文字 | 置かれるもの | 理由のメモ |
|---|---|---|
| `/vote` `/v` `/投票` | 投票 | 任意 |
| `/votemust` `/必須` | 投票（理由必須） | NG と保留では必須 |

- 議題は空でもよい。そのときはボタンだけの行になる
- 1人1票。選び直し・取り消し（選んでいるボタンをもう一度押す）ができる
- 押した人ごとに、改行を含むメモを残せる（「なぜ NG か」「なぜ保留か」を書く欄）
- 票やメモを変えると前の内容を履歴に残す。一覧に「変更あり」と出て、押すと経緯が並ぶ
- 理由必須かどうかは作るときに決め、あとから変えない

相手先（顧客）も押せる。さらに相手先は、ポータルの Wiki と議事録に「普通の行」と「メモ」だけを書き足せる（§5）。

## 2. 画面の動き

- ボタンには人数を出す。自分の選んだボタンは押された見た目になる
- 押した人は、選んだボタンごとに名前・押した時刻・メモを並べる
- 理由必須の投票で NG・保留を押すと、すぐには送らず理由の欄を開く。書くまで「NG で送る」は押せない
- メモの欄は本文の外に浮かせて出す。本文の中に入力欄を置くと、Enter で行が分かれるなど、打った字をエディタが先に拾うため
- 押すと返事を待たずに画面を変える。失敗したら元に戻し、理由を出す
- ほかの人の票は、開いたとき・画面に戻ったとき・自分が押したあとに読み直す。会議中にすぐ出す仕組みは §6
- 読むだけの権限の人（viewer）も押せる。投票を置けるのは本文を編集できる人

## 3. 本文に持つもの

票は本文に書かず、DB の表に置く。本文に票を書くと、押すたびに本文の保存が走る。そうなると Wiki の楽観ロック（保存の前に他の人が書き換えていないか確かめる仕組み）や議事録の書記の保存とぶつかり、書きかけが消える。

### 3.1 Wiki

BlockNote のブロック `docPoll`。props は `pollId`（投票の番号）と `reasonRequired`（`none` / `ng_hold`）。議題はブロックの文字。

### 3.2 議事録（PR2）

Markdown の行 `<!--vote:uuid-->議題`（理由必須は `<!--vote:uuid must-->議題`）。会議メモの `<!--note:…-->` と同じ方式。

目印の形（Wiki の props 名、議事録の `<!--vote:…-->`）は文書に残るので、以後は変えない。

### 3.3 番号の振り直しと、投票の作成

番号は画面が作って本文に置き、DB の投票は本文を編集できる人の画面が作る。通信を待たずにブロックを置くためで、`DocPollHost` が本文の変化を見て次のことをする。

- **DB に無い番号**（置いた直後・作り損ねたもの）は作る
- **同じ文書の中で番号が重なった**（コピーして貼った）ら、貼った側を新しい番号にして作る。前からあったブロックが番号（＝集まった票）を持ち続ける。元の投票の上に貼っても同じ
- **別の文書の番号**（別のページからコピーした）は、DB が「使用中」と返すので新しい番号にする
- 振り直しは「元に戻す」の履歴に載せない。載せると、貼り付けを Ctrl+Z で戻すときに振り直しだけが戻り、貼る前に戻れなくなる
- 一瞬つながらずに作れなかったときは1回だけ作り直す。それでも作れない、または権限が無いときは、そのブロックに「用意できませんでした」と出す

振り直すと本文が変わるので保存が走る。重なった番号の本文を編集できる人が開いただけでも起きるが、重なるのは貼り付けの直後だけで、そのとき貼った人の画面が振り直すので、ほかの人が開いて起きることはほぼ無い。

## 4. DB（PR1）

migration: `supabase/migrations/20260926083057_doc_polls.sql`、検証: `supabase/tests/run_doc_polls.sh`

| 表 | 中身 |
|---|---|
| `doc_polls` | 投票1つ。`wiki_page_id` か `meeting_id` の片方・`reason_required`・作った人。作ったあとは変えない（更新はトリガーで拒否） |
| `doc_votes` | 今の票。1人1行（`poll_id, user_id` が主キー）。`choice` は ok / ng / hold、`memo` は2000字まで |
| `doc_vote_events` | 履歴。cast（初めて押した）/ change（選び直した・メモを直した）/ retract（取り消した）。追記だけ |

文書の種類ごとに列を分けた。1つの列に文書の番号を入れて種類で見分ける形（多相キー）は外部キーが張れず、文書を消しても投票が残る。

### 4.1 書き込みは関数だけ

3表とも、ログインした人（authenticated）に insert / update / delete を与えない。社内も相手先も、自分のログインのまま同じ関数を呼ぶ。サーバーの特権キー（service role）は使わない。

- `rpc_doc_poll_create(p_poll_id, p_wiki_page_id, p_meeting_id, p_reason_required)`：作れるのは文書の space に書ける社内メンバー（`app_can_write_space`）。space と org は文書から取る。同じ番号・同じ文書の再送はそのまま通す
- `rpc_doc_vote_cast(p_poll_id, p_choice, p_memo)`：`p_choice` が null なら取り消し。1人1票・理由必須・履歴の追記をここで守る。同じ内容で押し直したときは何も書かない

関数は RLS（DB 側で行ごとに読み書きを制限する仕組み）を通らないので、二要素認証の条件（`mfa_satisfied`）も関数の中で確かめる。

### 4.2 読める人

`app_can_read_doc_poll(poll_id)` の1か所で決め、3表の読み取りと `rpc_doc_vote_cast` の両方がこれを見る（読める人＝押せる人）。

- PR1：社内（`app_is_space_internal`。viewer を含む）
- PR3 で足した：相手先。条件は `app_can_read_doc_poll` の1か所にある
  - **議事録**：その会議を読める人（進行中・終了の会議。予定の会議は読めない）
  - **Wiki**：投票1つずつで決める。「公開中のマイルストーンに公開した控えに載っていて、今の元ページにも残っている投票」だけ。相手先に見えるのは公開した控えなので、公開のあとに社内が元ページへ足した投票（社内だけの相談）は読めない。元ページから消した投票も押せない（社内に見えない票が溜まるのを防ぐ）
  - 公開したあとに社内が貼り直して番号が変わった投票は、相手先の控えでは「この投票は終了しました」と出る。公開し直せば押せる
  - 判定は本文に投票の番号（uuid の文字列）が含まれるか。公開の記録の表は作らない（控え自体が「何を公開したか」の記録。Fable 裁定・2026-09-26）
- **相手先に公開したページ・相手先が入る会議の投票では、社内の人の名前・選んだもの・メモ・経緯も相手先に見える**。メモに社内向けの話を書かない

押した人の名前・選んだもの・メモは、その文書を読める人全員に見せる。隠すと「誰が保留にしたか」を会議で使えない。メールアドレスは返さない。

### 4.3 エラーの返し方

| SQLSTATE | 印 | 画面の言葉 |
|---|---|---|
| 42501 | forbidden | この投票には押せません（存在しない投票も同じ返事にする） |
| 22023 | reason_required | NG と保留は理由を書いてください |
| 22023 | memo_too_long | メモは2000字までです |
| 22023 | poll_id_in_use | （画面には出さない。番号を振り直す） |

## 5. 相手先が行とメモを書き足す（PR5・PR6）

相手先に本文を丸ごと保存させない。サーバーも本文（`wiki_pages.body` / `meetings.minutes_md`）と `updated_at` を触らない。

- 相手先の書き足しは、差し込みの台帳 `doc_insertions` に「反映待ち」で置く。中身は普通の行かメモだけで、字と改行のほかは受け付けない
- 本文に入れるのは社内の編集画面（同時編集中は書記のタブ）。取り込んでいつもどおり保存し、そのあと反映済みにする。本文の目印（議事録 `<!--ins:uuid-->`、Wiki の props `insertionId`）で二重に入らないようにする
- 反映待ちの間は、相手先の画面にも社内の画面にも本文と重ねて表示する。PDF・CLI・検索など本文だけを読む経路には、社内の誰かがページを開くまで出ない（画面では「反映待ち」と出す）
- 差し込み先の行が直前に書き換えられて見つからないときは、文書の末尾に付けて印を残す
- 相手先は自分が足したものを丸ごと消せる（編集はできない）。反映待ちなら取り下げ、反映済みなら社内の画面が消す。社内の人がその下に字下げして書き足していたら消せない
- 誰が足したかは台帳で判定する。本文に添えた名前は社内の人が書き換えられるので使わない

サーバーが本文を直接書いて全員に読み直させる方式は採らない。会議中に社内の打ちかけが消えるため。

### 5.1 作り（Fable 裁定・2026-09-26 の変更を含む）

- **入口は DB の関数3本**（本人のログインのまま呼ぶ・投票と同じ型。当初のポータル API 案から変更）
  - `rpc_doc_insertion_create`：文書を読める相手先が作る。space と org は文書から取る。1人×1文書の反映待ちは20件まで。本文は1〜2000字で、改行以外の制御文字は不可
  - `rpc_doc_insertion_mark_applied` / `rpc_doc_insertion_mark_removed`：社内の編集者だけ。**本文に目印が入った（消えた）ことを DB で確かめてから**状態を進める。保存の前にタブが閉じても、反映済みの印だけが先に立つことはない
  - `rpc_doc_insertion_withdraw`：本人だけ。反映待ちなら取り下げ、反映済みなら削除依頼
- **状態**：`pending`（反映待ち）→ `applied`（反映済み）／`pending` → `withdrawn`（取り下げ）／`applied` → `remove_requested`（削除依頼）→ `removed`（削除済み）
- **表 `doc_insertions`**：ログインした人には読み取りだけ。社内は文書の分を全部、相手先は自分の行だけ読める
- **本文での表し方**：ブロック `docInsertion`（props: insertionId・kind・createdAt・author）。行もメモもこの1種類で、見た目を kind で分ける（メモ＝会議メモと同じ帯、行＝普通の行＋右端に名前と日時）。「/」メニューには出さない。コピーして外へ貼ると本文だけが出る
- **議事録の目印**：`<!--ins:<番号> <kind> <日時> <名前>-->本文`（続く行は `<!--ins-->本文`）。名前は4欄目以降の全部。**形は以後変えない**
- 社内は相手先が足した行を本文でふつうに直したり消したりしてよい（今の文書として正しいのは本文。台帳は「誰が・いつ・何を出したか」の記録）
- 議事録は字下げした子の行を保存で平らにするので、「下に子の行があれば消せない」は Wiki だけの決まり


## 6. その場の反映（PR2・PR4）

合図だけを送る private チャネル `meeting-minutes-view:<会議ID>` を足す。中身は `minutes-saved` / `insertion-changed` / `vote-changed` の合図だけで、本文は運ばない。受け取った画面が RLS 越しに読み直す。

- 入れるのは、その会議の space に入れる人（社内・相手先とも）で、二要素認証の条件を満たす人
- 偽の合図が送られても、起きるのは「読み直し」だけ。見える範囲は RLS が決める
- 同時編集のチャネル `meeting-minutes:<会議ID>` には相手先を入れない。中身は同時編集の差分で、部屋の履歴を持たない画面には使えない
- Wiki も同じ形で `wiki-page-view:<ページID>` を使う（ユーザー要望・2026-09-26）

いま（2026-09-26・migration `20260926114116_doc_vote_signal.sql`）は `vote-changed` だけを送る。入れるのは投票を読める社内メンバー（`app_can_read_doc_poll` と同じ条件。読むだけの人も含む）＋二要素認証の条件で、判定は `app_can_join_doc_vote_signal(topic)` の1か所。相手先は PR3・PR4 でこの関数に足す。

- 押した画面は、送り終えたあとに合図を送る（`useDocVoteSignal`）。受けた画面は票を読み直す。自分の送信の途中に届いた合図では読み直さず、送り終えたときの読み直しに任せる
- つながるたびに1回読み直す（つなぐ前・切れていた間に押された票を拾う）。サーバーに閉じられた（CLOSED）ときもやり直す
- 続けて届いた合図は 400ms まとめて1回だけ読み直す（大勢が同時に押すと、1回ずつでは人数の2乗の取得になる）
- 議事録の定期の読み直しは、つながっている間は60秒ごと（取りこぼし用）、つながらないときは5秒ごと。Wiki は定期には読み直さない

### 6.1 相手先ポータルの議事録をその場で出す（PR4）

- 社内の議事録の画面は、保存が通るたびに同じチャネルへ `minutes-saved` を送る（本文は運ばない）
- 相手先ポータルは、**進行中の会議**を開いている間だけこの知らせを待ち、届いたら本文の列（`minutes_md`）だけを RLS 越しに読み直す（`useLiveMinutes`）。社内は入力が止まるたびに保存し、本文は数百KBになるので、読み直しは**5秒に1回まで**（最後の知らせは必ず反映）。取っている間は重ねない。画面が裏に回っている間は取らず、表に戻ったら1回。チャネルにつながった直後にも1回。つながらないときの保険に60秒ごと
- 投票の無い進行中の会議は、チャネルだけを張り、投票は読まない
- 終了した会議で投票の無いものは、チャネルも張らない
- チャネルは1文書1本（同じ名前を2本開くと互いに閉じ合う）。知らせは種類（`vote-changed` / `minutes-saved`）で振り分ける

## 8. 着手前に確かめること

- （済）投票をコピーして外へ貼ると、印と議題だけが出る（`toExternalHTML`）。押した人の名前とメモは付いていかない
- 票の履歴はページの全投票の分を毎回読む。数百件までは問題ない。増えたら件数だけを読み、中身は「変更あり」を開いたときに読む形にする

- 議事録の Markdown が、段落の下に字下げした子の行を保存と読み込みで保てるか。保てないなら「下に子がある行は消せない」は Wiki だけの決まりにする（PR5 の前）
