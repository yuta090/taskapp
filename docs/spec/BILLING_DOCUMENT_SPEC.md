# 見積書・請求書の外部連携 仕様

**版**: v1.0（2026-07-26）
**関連**: `spec/ESTIMATE_WORKFLOW_SPEC.md`（TaskApp内での見積もり合意）, `src/lib/integrations/registry.ts`（連携カタログ）

---

## 0. 範囲（厳守）

この連携が扱うのは **見積書・請求書の作成** と、**その状態（発行済み・入金済みなど）の取り込み** だけ。

**扱わないもの**: 仕訳、入出金明細、経費、決算、勘定科目、税務申告 — つまり会計データ全般。

> **表現の約束**
> UI・LP・営業資料で「freeeと連携」「マネーフォワードと連携」「会計連携」とだけ書いてはいけない。
> それらは会計データ全般が同期されると読まれる。必ず **「見積書・請求書の作成」** まで書き切る。
> カテゴリ名も `会計・請求` ではなく `見積書・請求書の作成` を使う。

## 2. 発行の単位

**タスクを複数選んで1枚にまとめる**。1件だけ選べば「1タスク＝1枚」にもなるため、月次の一括請求と単発の見積の両方を同じ画面で賄える。

- 明細は「タスク1件＝1行」。数量は常に 1、単価は `task_pricing.sell_total`
  （TaskApp の金額はタスク単位の総額であり、工数×単価に割り戻すと端数が出るため）
- 税率は書類単位で 10% / 8%（軽減）/ 非課税 から選ぶ（TaskApp は品目ごとの税率を持たない）

## 3. 守る不変条件

### 3.1 二重発行しない（最優先）

同じ請求書が2通、取引先に届くのは謝って済む話ではない（入金消込が壊れ、信用を落とす）。ネットワークの再送・二度押し・ブラウザの復元のいずれでも起きうるため、**アプリ側の「送信中は押せない」では防げない**。

**2段で守る:**

1. **外部を叩く前に発行記録を作る** — `billing_documents(org_id, provider, doc_type, idempotency_key)` の一意制約。二度押しの2回目はここで弾かれ、外部APIに到達しない
2. 成功したら同じ行を更新 — 応答を取りこぼしても行は残るので「送ったか分からない」状態にならない

**順序を逆にしてはいけない。** 先に外部へ出してから記録すると、記録に失敗した瞬間に「台帳から消えた請求書が取引先の手元にだけ存在する」状態になる。

外部で失敗したときは記録を削除する（残すと同じ内容を永久に再発行できなくなる）。

**冪等キー** = `sha256(spaceId | docType | partnerId | issueDate | subtotal | sorted(taskIds))`
タスクIDを**並び替えてから**混ぜるのが要点。画面での選択順は毎回変わりうるので、順序を残すと「同じ内容なのに違う鍵」になり二重発行を素通しさせる。
逆に、金額を直した・対象を変えた・日を改めた場合は別の鍵になるため、正当な再発行は妨げない。

### 3.2 金額未入力を0円で通さない

選んだタスクに金額未入力が1件でもあれば **422 で止める**。0円として黙って通すと、請求漏れが「請求済み」の記録だけ残して発覚しなくなる。出す前に止めるほうが安い。

### 3.3 未知の状態で既知の状態を潰さない

外部のステータスは `draft / issued / paid / accepted / canceled / unknown` に畳む。畳めない値は `unknown` に落とし、**既存の status を上書きしない**（生の値は `raw_status` に残す）。
発行済みが「不明」に戻ると督促の判断材料が消える。また未知の値を `paid` に寄せると、未入金の請求を入金済みと誤認して取りはぐれる。

### 3.4 取引先を自動作成しない

会計側の取引先マスタは請求・入金消込の土台であり、表記ゆれた重複行が増えると経理の実務が壊れる。**既存の取引先から人が1度選ぶ**（`accounting_partner_links`、1スペース×1サービスで1件）。

## 4. 権限

| 操作 | 権限 |
|---|---|
| サービスへの接続（OAuth） | org の owner/admin のみ。接続は `owner_type='org'` |
| 取引先の選択・変更 | スペースの admin/editor |
| 発行 | スペースの admin/editor |
| 発行履歴の閲覧 | 内部メンバー（RLS `app_is_org_internal`） |
| CSVの金額列 | スペースの admin/editor |

接続を org 単位かつ管理者限定にするのは、**会社の請求アカウントに繋がる**ため。誰でも張り替えられると請求書の発行元がすり替わる。

CSVの金額列を admin/editor 限定にするのは、**ベンダーに請求金額（売値）が渡ると利益率がそのまま知られる**ため。viewer/vendor では列ごと落とす（空欄で残すと「0円」と誤読される）。

## 5. 状態の取り込み

`/api/cron/accounting-sync` を **2時間おき**（毎時17分）に起動する。

- 対象は未確定の書類のみ（`draft / issued / unknown`）。`paid / canceled / accepted` は終端なので呼ばない
- 1回あたり最大50件、同じ書類は30分以内に引き直さない
- 1件の失敗で全体を止めない。失敗した書類も `remote_synced_at` を進める
  （進めないと恒久的に失敗する1件が毎回バッチの先頭に居座り、後続が永久に確認されない）

## 6. データモデル

| テーブル | 役割 |
|---|---|
| `accounting_partner_links` | スペース ↔ 会計側の取引先（1スペース×1サービスで1件） |
| `billing_documents` | 発行記録。二重発行の歯止め |
| `billing_document_tasks` | 書類に含めたタスク。二重請求の**警告**用（分割請求・再請求は正当なので禁止はしない） |

全て 読取=内部メンバーのみ / 書込=service role のみ。金額と取引先が入るため client ロールには一切見せない。

## 7. 主要ファイル

```
src/lib/accounting/
├── types.ts          # アダプタ境界。範囲（書類のみ）の約束もここ
├── adapters.ts       # server専用の登録簿
├── implemented.ts    # client安全なID一覧（値importを持たない）
├── http.ts           # 共通HTTP境界（失敗の分類を1本化）
├── oauth.ts          # 3社のOAuth（URLとスコープだけが違う）
├── connection.ts     # 未接続/失効/一時障害を区別して返す
├── issue.ts          # 冪等キー・明細組み立て（純粋関数）
├── sync.ts           # 状態の取り込み
└── providers/{freee,moneyForward,misoca}.ts

src/app/api/accounting/{documents,partners}/route.ts
src/app/api/cron/accounting-sync/route.ts
src/app/(internal)/[orgId]/project/[spaceId]/views/billing/
```

**各社固有のリクエストボディは `buildDocumentPayload()` に閉じ込める。** 仕様のズレはこの1関数の修正で吸収できるようにしてある。
